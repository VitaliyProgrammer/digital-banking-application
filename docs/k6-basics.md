## 🧩 1. Навіщо це взагалі

Unit- та інтеграційні тести перевіряють **правильність** на одному запиті. Але багато проблем видно лише під навантаженням:

| Проблема | Чому її не видно без навантаження |
|---|---|
| 🔒 Блокування («гарячий рядок») | один запит не має з ким конкурувати за рядок |
| 🔌 Вичерпаний пул з'єднань з БД | 10 з'єднань вистачає одному клієнту, але не сорока |
| 🐢 Повільний запит без індексу | на 10 рядках швидко, на мільйоні ні |
| 🧠 Витік пам'яті | видно лише за години роботи |
| 🏁 Race condition | потрібні два запити **в ту саму мить** |

У нашому банку k6 знайшов саме перше: усі перекази стояли в черзі за одним рахунком комісій. 0% помилок, але повільно.

## 📖 2. Словник: ключові слова k6

| Термін | Що це | Приклад |
|---|---|---|
| **VU** (virtual user) | віртуальний користувач: окремий «клієнт», який крутить твій сценарій по колу | `vus: 40` — сорок одночасних клієнтів |
| **iteration** | один прохід функції `default` одним VU | зайшов → подивився рахунок → переказав |
| **default function** | сценарій одного клієнта | `export default function () { … }` |
| **setup()** | виконується **один раз** до тесту; результат отримує кожен VU | створити 40 клієнтів з грошима |
| **teardown()** | **один раз** після тесту | перевірити, що гроші зійшлись |
| **options** | налаштування тесту: скільки VU, як довго, пороги | `export const options = { … }` |
| **scenario** | іменований план навантаження зі своїм executor | `busy_day`, `one_hot_account` |
| **executor** | *як* подавати навантаження (див. розділ 4) | `ramping-vus`, `constant-vus` |
| **stages** | етапи зміни кількості VU | 1 хв розгін → 3 хв пік → 30 с спад |
| **check** | перевірка відповіді; **не зупиняє** тест, а рахує % успіху | `check(r, { 'status 201': r => r.status === 201 })` |
| **threshold** | умова успіху **всього** тесту; не виконана → exit code 99 | `http_req_duration: ['p(95)<500']` |
| **think time** | пауза «людина думає» між діями | `sleep(1)` |
| **tags** | мітки запитів, щоб рахувати метрики окремо | `{ name: 'transfer' }` |
| **group** | логічна група запитів у звіті | `group('login', () => …)` |

## 📊 3. Метрики: що міряє k6

| Метрика | Що означає |
|---|---|
| `http_req_duration` | повний час запиту: відправити → дочекатись → отримати відповідь |
| `http_req_waiting` | **TTFB** (time to first byte): скільки сервер думав |
| `http_req_failed` | частка невдалих запитів (за замовчуванням усе, крім 2xx/3xx) |
| `http_reqs` | кількість запитів і **RPS** (requests per second) |
| `iterations` | скільки разів пройдено сценарій |
| `vus`, `vus_max` | скільки VU активні зараз і максимум |
| `checks` | частка успішних check |

### 📐 Перцентилі: найважливіша думка

**p95 = 500 мс** означає: 95% запитів швидші за 500 мс, а 5% повільніші.

| Чому не середнє (avg) | |
|---|---|
| 99 запитів по 100 мс + 1 запит 10 с | **avg = 199 мс**, «все добре» |
| | **p99 = 10 с**: кожен сотий клієнт чекає 10 секунд |

Середнє ховає погані випадки, а перцентилі їх показують. Тому пороги завжди ставлять на **p95 / p99**, а не на середнє.

## 🚦 4. Executors: як подавати навантаження

| Executor | Що робить | Коли брати |
|---|---|---|
| `constant-vus` | фіксована кількість VU на час | «30 клієнтів б'ють хвилину» (наш contention) |
| `ramping-vus` | VU ростуть і спадають по `stages` | реалістичний день: люди приходять поступово (наш load) |
| `constant-arrival-rate` | фіксовані **запити за секунду**, хоч скільки VU знадобиться | «витримаємо 100 RPS?» |
| `ramping-arrival-rate` | RPS росте по етапах | шукати межу системи |
| `per-vu-iterations` / `shared-iterations` | фіксована кількість ітерацій | разові сценарії |

💡 **Closed model** (`*-vus`): новий запит іде лише після відповіді на попередній, тому повільна система сама собі зменшує навантаження. **Open model** (`*-arrival-rate`): запити йдуть із заданою частотою, хоч би як повільно відповідав сервер. Так поводяться справжні користувачі в інтернеті.

## 🧪 5. Види навантажувальних тестів

| Тип | Профіль | Питання |
|---|---|---|
| 💨 **Smoke** | 1–2 VU, 30 с | чи взагалі працює? (перед будь-яким іншим тестом) |
| 📈 **Load** | очікуване навантаження, хвилини | чи тримає звичайний день у межах SLO? |
| 💥 **Stress** | більше за норму, поступово | де межа і **як** система ламається: повільніє чи падає? |
| ⚡ **Spike** | різкий стрибок | що буде о 9:00 у день зарплати? |
| 🕰️ **Soak** (endurance) | норма, години | витоки пам'яті, переповнені логи, деградація з часом |
| 🏁 **Contention** | багато VU на **один** ресурс | гонки, блокування, коректність (наш банк: один рахунок) |

## ✍️ 6. Мінімальний скрипт

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 20 },  // розгін до 20 VU
    { duration: '1m',  target: 20 },  // тримаємо
    { duration: '10s', target: 0 },   // спад
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],   // < 1% помилок
    http_req_duration: ['p(95)<500'], // 95% швидші за 0.5 с
  },
};

export default function () {
  const res = http.get('http://localhost:8080/exchange-rates');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1); // think time
}
```

```bash
k6 run script.js                                           # локально
docker run --rm -i grafana/k6 run - < script.js            # без встановлення
docker compose --profile load run --rm k6 run /scripts/load.js   # у цьому проєкті
```

## 🧠 7. Типові помилки (усі я зробив або побачив у цьому проєкті)

| Помилка | Наслідок | Як правильно |
|---|---|---|
| Без `sleep` | 40 VU поводяться як тисячі клієнтів | додати think time |
| Холодна JVM | перший прогін міряє JIT-компіляцію, а не систему | прогріти або порівнювати теплий з теплим |
| Пороги на середньому | погані випадки сховані | p95 / p99 |
| Очікувані 4xx рахуються помилками | хибні «failed» | `http.setResponseCallback(http.expectedStatuses(200, 201, 422))` |
| Генератор навантаження на тій самій машині | k6 відбирає CPU в системи, яку тестуєш | окрема машина для k6 (у production-тестах) |
| «Помилок 0%, отже все ок» | черга видна лише в p95 і в пулі з'єднань | дивитись на перцентилі і на метрики сервера |
| Лагодити і не міряти знову | не знаєш, чи допомогло | **after > before**: та сама методика, ті самі умови |

## 🎤 8. На співбесіді: як розповісти

> «Я написав три k6-сценарії: smoke, load на 40 VU і contention, де 30 VU знімають гроші з одного рахунку. Load не пройшов пороги при 0% помилок: p95 переказу був 890 мс. За метриками HikariCP запити чекали на з'єднання, а в `pg_locks` я побачив, що всі перекази стоять у черзі за одним рядком рахунку комісій банку. Я розбив гарячі рахунки банку на 16 шардів, і p95 переказу впав до 483 мс, на 46%. Contention довів, що навіть під гонкою баланс сходиться до копійки, а повтор з тим самим Idempotency-Key не списує двічі.»

Ця відповідь показує не «вмію запустити k6», а **цикл роботи інженера**: виміряв → знайшов причину → виправив → довів цифрами.
